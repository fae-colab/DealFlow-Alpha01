# DealFlow — Append-only evidence lifecycle design

**Status:** Design proposal only — not implemented  
**Scope:** Prevent evidence revocation, withdrawal, and supersession from being silently undone; preserve reproducible historical decisions.  
**Target branch:** `test/adversarial-evidence-eligibility-v1`  
**Compatibility constraint:** Do not modify PR #29 or merge PR #30 as part of this design.

## 1. Problem and current gap

The current evidence evaluator accepts a mutable `status` snapshot (`active`, `superseded`, `revoked`, or `withdrawn`). It correctly excludes a retired status while evaluating a record, but it cannot establish how that status was reached, who changed it, when the change was recorded, or whether a later write silently changed it back to `active`.

The older `evidence.js` model has a `supersedesId` link for revised claim records. That helps identify a current record, but does not provide a complete lifecycle audit trail for revocation or withdrawal. The outcomes module demonstrates an append-only event pattern, but evidence needs stricter state-transition and concurrency rules.

**Design principle:** evidence content is immutable; lifecycle state is a projection of an append-only event log. A status field supplied by a caller, import file, or UI is never authoritative.

## 2. Core model

Persist two separate collections:

1. `evidenceRecords[]`: immutable evidence payloads. Once created, an evidence record's claim, value, source, observation timestamps, provenance, and evidence ID never change.
2. `evidenceLifecycleEvents[]`: append-only lifecycle events. These are the sole authority for whether a record is active, superseded, revoked, or withdrawn.

Do not overwrite an evidence record to correct it. Create a new record with a new globally unique ID, then append an event that supersedes the old record.

### 2.1 Immutable evidence record

Retain the existing claim/provenance fields and add/standardize:
- `evidenceId`: globally unique, immutable ID.
- `claimId` / `evidenceType` (or the existing subject/claim-key pair): stable claim identity.
- `contentHash`: hash of canonical immutable payload, excluding lifecycle status and mutable UI metadata.
- `createdAt`: optional source-side creation time if known; it is not a substitute for DealFlow's event-log recorded time.

Remove `status` as a writable source of truth. For compatibility, legacy `status` may be retained as `legacyStatusSnapshot` during migration, clearly marked non-authoritative.

### 2.2 Lifecycle event schema

Each event is immutable and contains:

```json
{
  "eventId": "life-<unique-id>",
  "sequence": 42,
  "eventType": "evidence_created",
  "evidenceId": "EV-123",
  "claimKey": "buyer_readiness",
  "recordedAt": "2026-11-13T20:30:00.000Z",
  "effectiveAt": "2026-11-13T20:30:00.000Z",
  "recordedBy": "agent-or-system-actor",
  "reasonCode": "INITIAL_CAPTURE",
  "reason": "Initial evidence capture",
  "replacementEvidenceId": null,
  "requestId": "operation-unique-id",
  "previousEventHash": "<hash-or-genesis>",
  "eventHash": "<hash-of-canonical-event>"
}
```

Field rules:
- `eventId` is globally unique.
- `sequence` is strictly increasing within one ledger; never re-used.
- `recordedAt` is generated by the app/storage boundary at append time and cannot be user-backdated.
- `effectiveAt` is when the actor says the lifecycle change took effect. It may be earlier than `recordedAt`, but must never replace it. Current eligibility changes when the event is recorded, not retroactively at the backdated effective time.
- `recordedBy` identifies the actor label, not authenticated identity unless a real authentication mechanism is added.
- `reasonCode` and non-empty `reason` are mandatory for revocation, withdrawal, and supersession.
- `replacementEvidenceId` is mandatory for supersession and null for other event types.
- `requestId` makes retries idempotent and helps diagnose duplicate submissions.
- Hash fields are optional in the first local-only implementation, but required before describing the log as tamper-evident. Hash canonicalization and external anchoring are specified in section 8.

Recommended event types:
- `evidence_created`
- `evidence_superseded`
- `evidence_revoked`
- `evidence_withdrawn`

There is deliberately no `evidence_reactivated`, `status_set_active`, or generic `status_changed` event.

## 3. State machine and transition rules

A record with exactly one valid `evidence_created` event starts `active`. The following transitions are permitted:

| Current projection | Event | Result | Conditions |
|---|---|---|---|
| Does not exist | `evidence_created` | active | Record exists; unique ID; payload hash matches |
| active | `evidence_superseded` | superseded | Replacement record exists, is newly created in same atomic operation, and refers to the same claim |
| active | `evidence_revoked` | revoked | Reason and actor required |
| active | `evidence_withdrawn` | withdrawn | Reason and actor required |
| superseded | any lifecycle transition | reject | Terminal state |
| revoked | any lifecycle transition | reject | Terminal state |
| withdrawn | any lifecycle transition | reject | Terminal state |

Rules:
1. A record can have one creation event and at most one terminal lifecycle event.
2. A terminal transition is irreversible. A second transition, including a second supersession, is rejected.
3. Supersession is one-to-one: one prior record can have only one replacement. If a replacement itself is corrected, supersede the replacement, creating a chain; do not branch from the original.
4. A replacement must have a new evidence ID and the same claim identity. It may have a different value/source/provenance because it represents the correction or newer observation.
5. The replacement record and the supersession event must be appended as one logical transaction. If either fails validation, neither is committed.
6. A revoked or withdrawn record is never reactivated. If the underlying information later becomes valid, capture it as a new evidence record and explain the new provenance.
7. An event referencing an unknown evidence ID, a replacement with a different claim identity, a duplicate event ID, an invalid actor, or an invalid transition causes the entire import/append operation to fail closed.
8. Event order is determined by `sequence`, not array order or client timestamps. Array order is validated against sequence and hash links.

### 3.1 Expiry is derived, not a lifecycle transition

`expired` remains a derived eligibility condition from immutable `validUntil` and the evaluation instant. Do not append an expiry event merely because time passed. Once expired, the record cannot support a current decision; new evidence receives a new ID. An explicit supersession event may still link the expired record to its replacement for audit lineage, but it must not make the expired record active again.

## 4. Deterministic lifecycle projection

Implement a pure projection function:

```text
projectEvidenceLifecycle(evidenceRecords, lifecycleEvents, asOfRecordedSequence)
  -> { evidenceId, status, createdEventId, terminalEventId, replacementEvidenceId }
```

For each evidence ID:
- Require exactly one creation event.
- Require zero or one terminal event.
- Validate all event references and transition preconditions.
- Derive status from the event chain; never read `record.status` as authority.
- Derive expiry separately from `validUntil <= evaluationAsOf`.
- Reject malformed chains rather than guessing a current status.

Decision Desk integration:
- Evaluate only records whose projected status is `active` at the selected ledger watermark.
- Pass the projected status to the existing evidence evaluator as an internal, derived value; do not accept caller-supplied status.
- Include evidence IDs, immutable content hashes, and the lifecycle ledger watermark in every recommendation snapshot.
- A new run uses the latest valid ledger sequence. A historical replay uses the sequence captured by that snapshot, reproducing what DealFlow knew at that time.

## 5. Time semantics: current decisions vs historical replay

This distinction is essential:

- `recordedAt` answers: when did DealFlow learn and record this lifecycle change?
- `effectiveAt` answers: when does the actor say the change was applicable in the real world?

A revocation discovered today but believed to have been effective yesterday is appended today with yesterday's `effectiveAt` and today's `recordedAt`. All new recommendations exclude the record immediately after the revocation event is appended. A historical recommendation created before the event remains reproducible as an **as-known-at-the-time** decision; it must not be silently rewritten. A separate retrospective review may flag that later information would have changed the evidence assessment.

Never replay old decisions using the latest lifecycle projection unless the explicit question is a retrospective reassessment. Label these two modes distinctly:
- `AS_KNOWN_AT_DECISION`
- `RETROSPECTIVE_WITH_LATER_EVIDENCE`

## 6. Atomic append API and validation

Expose only narrow operations; do not expose a generic setter for lifecycle status:

- `appendEvidenceRecord(record, expectedLedgerSequence)`
- `supersedeEvidence(oldEvidenceId, replacementRecord, reason, actor, expectedLedgerSequence)`
- `revokeEvidence(evidenceId, reason, actor, expectedLedgerSequence)`
- `withdrawEvidence(evidenceId, reason, actor, expectedLedgerSequence)`
- `projectEvidenceLifecycle(...)`
- `validateEvidenceLifecycle(...)`

Every append operation must:
1. Load the latest ledger revision.
2. Verify `expectedLedgerSequence` equals the current sequence; otherwise reject with a concurrency conflict and require reload/retry.
3. Validate immutable record schema, event schema, unique IDs, claim identity, allowed transition, timestamps, actor, reason, and hash continuity.
4. Construct the next event internally; callers cannot supply sequence, recordedAt, previous hash, or projected status.
5. Append the record/event batch atomically.
6. Re-read and validate the committed ledger before reporting success.

Idempotency:
- Repeated `requestId` with the same payload returns the original result and does not append a second event.
- Repeated `requestId` with a different payload is an integrity error.
- A second terminal event for the same evidence ID is always rejected, even if it has a different request ID.

## 7. Migration and compatibility

Do not silently infer historical events that the current data never recorded.

Migration plan:
1. Preserve every existing evidence record byte-for-byte as a legacy payload, adding only a stable immutable content hash in the new envelope.
2. Create one `evidence_created` migration event per existing record with `recordedAt` equal to migration time and `recordedBy: "legacy_migration"`. Do not pretend that the old `capturedAt` or `recordedAt` field is the time DealFlow first recorded it unless its meaning is proven.
3. For existing `supersedesId` links, validate that the predecessor exists, the claim identity matches, and there is at most one successor. Append corresponding `evidence_superseded` migration events. Invalid/cyclic/branching links block migration for manual repair; do not discard records.
4. For legacy `status` values of `revoked` or `withdrawn`, create migration terminal events only if the status was explicitly stored and preserve the original field as `legacyStatusSnapshot`. Record that the reason/actor may be unknown; use `legacy_migration` as the actor and a specific `LEGACY_STATUS_IMPORT` reason code. If provenance is ambiguous, quarantine the record for review instead of assuming active.
5. Treat `expired` as derived from `validUntil`, never as a stored lifecycle state.
6. Retain a migration report: record count, event count, unresolved links, ambiguous legacy statuses, and content hashes.
7. Bump the state/evidence schema version. Keep a read-only compatibility adapter for older backups; do not mutate the source backup during validation.

## 8. Tamper evidence, persistence, and honest guarantees

There are three distinct guarantees; do not conflate them.

**A. Application-level append-only behavior (minimum local prototype):**
- UI and module APIs cannot edit or delete prior evidence records/events.
- All changes go through validated append operations.
- Export/import validates the entire chain.
- Snapshots store the ledger watermark and evidence hashes.

This prevents accidental edits through normal DealFlow workflows, but a user with browser developer tools can still edit or replace localStorage or a backup.

**B. Tamper-evident local ledger (recommended next step):**
- Canonicalize event fields in a fixed, documented key order and UTF-8 encoding.
- Calculate SHA-256 over the canonical event payload plus `previousEventHash`.
- Each event references the previous event hash; the first references a fixed genesis value.
- Validate the entire chain on load, before every append, and on import.
- Keep periodic signed/exported checkpoints outside the browser profile.

A hash chain detects accidental or partial alteration, deletion, insertion, and reordering. It does **not** stop an attacker who can rewrite the entire local log and recompute every hash.

**C. Strong non-repudiation / externally enforced immutability (future hosted service):**
- Append events to a server-side append-only store with authorization and audit logging.
- Use server-assigned sequence and timestamps.
- Anchor periodic ledger roots in a separately controlled store; optionally sign roots with a server-held key.
- Restrict deletion/update permissions at the storage layer and retain backups/WORM snapshots.
- Authenticate actors; a free-text `recordedBy` label alone is not proof of identity.

Until C exists, describe the local feature as **append-only by application contract and tamper-evident if hash anchoring is enabled**, not impossible to alter.

## 9. Recommendation snapshot integration

Each recommendation snapshot should capture:
- `evidenceLedgerSequence`
- `evidenceLedgerHeadHash`
- evidence IDs and immutable content hashes used for each claim
- derived lifecycle state at that sequence
- decision evaluation timestamp and mode (`AS_KNOWN_AT_DECISION` by default)

This allows:
- exact replay of the evidence available to the optimizer at decision time;
- audit of later revocation/supersession without rewriting old recommendations;
- a separate retrospective assessment using later lifecycle events.

A snapshot must fail validation if its recorded ledger head hash does not match the event at its recorded sequence.

## 10. Required executable tests before implementation approval

### Event integrity
1. One creation event projects to active.
2. Duplicate event IDs or evidence IDs are rejected.
3. Missing creation event, duplicate creation, unknown evidence reference, or invalid event type is rejected.
4. Sequence gaps, duplicate sequence numbers, reordered events, broken previous hash, or altered payload hash are rejected.
5. Event array permutation does not change projection after canonical sequence ordering; out-of-order stored sequence is rejected if physical append order is part of the storage contract.

### Irreversible transitions
6. Active → revoked works and projects revoked.
7. Active → withdrawn works and projects withdrawn.
8. Active → superseded works only with a valid replacement record for the same claim.
9. Revoked → active, withdrawn → active, superseded → active, and any second terminal event are rejected.
10. A replacement cannot supersede itself, a missing record, another claim's record, or create a cycle.
11. Two replacements for one predecessor are rejected.
12. Replacement record and supersession event are atomic: simulate failure at each stage and assert neither half is committed.
13. Expired records remain ineligible; adding new evidence does not revive the old record.

### Concurrency and retries
14. Two tabs append against the same expected sequence: first succeeds; second gets a conflict and cannot overwrite the first.
15. Same request ID and same payload is idempotent.
16. Same request ID with different payload is rejected.
17. Duplicate revocation retry does not create a second event.

### Replay and migration
18. A snapshot at sequence N remains AS_KNOWN_AT_DECISION after a revocation at N+1.
19. A retrospective replay at N+1 excludes the revoked record and labels the mode differently.
20. Legacy supersedesId chains migrate; branching/cyclic/dangling chains fail safely.
21. Legacy explicit revoked/withdrawn states are migrated with a visible legacy actor/reason and uncertainty.
22. Migration is idempotent and preserves original evidence content.
23. Backup import cannot silently remove or truncate an existing local event-log prefix.

### Decision Desk behavior
24. Decision Desk ignores caller-supplied `status: "active"` when the lifecycle projection says revoked.
25. Decision Desk uses only evidence active at the requested ledger watermark.
26. Recommendation snapshots retain evidence IDs, content hashes, ledger sequence, and head hash.
27. A corrupted or unavailable lifecycle ledger causes abstention, not fallback to a mutable status field.

## 11. Implementation sequence (after design approval)

1. Implement and test the pure lifecycle projection/validator with no UI or storage changes.
2. Add append operations and event schema; prove terminal-state irreversibility and atomic supersession.
3. Integrate Decision Desk so status is always derived from events.
4. Add state migration, backup validation, and snapshot ledger references.
5. Add concurrency protection and idempotency for browser multi-tab use.
6. Add hash-chain validation and checkpoint export; clearly state the local tampering limitation.
7. Run the full CI suite, new lifecycle suite, migration tests, and independent code-path review.
8. Only then consider a real-agent trial; no merge or pilot is implied by this design.

## 12. Explicit non-goals

- This design does not establish that evidence content is factually true.
- A lifecycle event records who/what DealFlow says made a change; without authentication it does not prove the actor's identity.
- Revocation does not automatically resolve contradictory evidence; it removes the revoked record from current eligibility and leaves the remaining evidence to be evaluated.
- The design does not add a source-authority hierarchy or freshness calibration.
- A local hash chain is not a substitute for a trusted remote audit service.

Review this design before implementation. In particular, approve or amend:
1. the four-event lifecycle vocabulary and terminal-state rules;
2. the distinction between `recordedAt` and `effectiveAt`, including as-known vs retrospective replay;
3. atomic replacement-plus-supersession;
4. legacy migration treatment where actor/reason history is missing;
5. whether Phase A (local append-only contract) is sufficient for Alpha, or whether SHA-256 chaining/checkpointing is required before any real-agent data is admitted.

## 13. Approved design decisions and binding amendments (2026-11-14)

**Decision status:** The owner approved items 1–3 and selected server-side protection for item 5. Item 4 (legacy migration) was approved only subject to the safeguards in this section. This section is authoritative wherever it tightens or supersedes earlier wording in this document.

### 13.1 Lifecycle state is not decision eligibility

The four event types and terminal-state rules in sections 2–3 are approved.

Keep lifecycle projection separate from evidence eligibility:
- Lifecycle states are `active`, `superseded`, `revoked`, and `withdrawn`.
- Eligibility is evaluated separately for a specific claim, decision, and evaluation time. An `active` record may still be expired, stale, malformed, contradicted, unverified, or otherwise ineligible.
- A terminal record is never reactivated. A correction or renewed observation receives a new evidence ID and new provenance. If a prior revocation was erroneous, record a new evidence record and an explanatory reference; do not erase or reverse the revocation.
- No client, import, or API caller may set lifecycle status directly.

### 13.2 Timestamp provenance and ordering

The timestamp rules in sections 2 and 5 are approved with these additions:
- Persist all event timestamps as UTC instants in a normalized RFC 3339 representation.
- `recordedAt` is assigned by the trusted server at commit time. Clients cannot supply or backdate it.
- `effectiveAt` is a claimed real-world effective time, not an ordering key. Store `effectiveAtBasis` as one of `source_verified`, `actor_reported`, `estimated`, or `unknown`, plus an optional source/reference and uncertainty note.
- Ledger sequence is the authoritative event order. `recordedAt` is audit metadata; neither client timestamps nor `effectiveAt` may reorder the ledger.
- Reject malformed timestamps. Future `effectiveAt` values require an explicit reason and must not affect current eligibility before the event is recorded. Preserve the submitted value and the validation decision; do not silently normalize a materially different time.
- Current decisions use the latest committed ledger watermark. Historical replay uses the exact sequence captured in the decision snapshot. Retrospective evaluation is a distinct operation and must be labelled as such.
- A later event never silently rewrites an earlier decision snapshot.

### 13.3 Transactional supersession

Supersession remains one logical transaction:
1. Authenticate and authorize the actor.
2. Verify the caller's expected ledger sequence/version.
3. Validate the replacement record, its immutable content hash, and same-claim identity.
4. Verify the predecessor is active at the transaction's serialization point and has no successor.
5. Insert the replacement record, its creation event, and the predecessor's supersession event atomically.
6. Enforce a unique successor constraint on the predecessor and a unique event sequence.
7. Commit all writes or none. Re-read the committed result and validate its chain before returning success.

A failed transaction must not leave an orphan replacement or a terminal predecessor without its replacement. A retry with the same idempotency key and identical canonical request returns the original committed result; the same key with different content is rejected.

### 13.4 Legacy migration: preserve, classify, dry-run, then commit

The migration rules in section 7 are amended as follows:

**Source preservation**
- Preserve the original backup as an immutable migration input. Record its cryptographic checksum, byte length, source format/version, and acquisition time.
- Do not describe a parsed-and-reserialized representation as byte-for-byte preservation.
- Migration operates on a copy. It never edits or deletes the source backup.

**Historical uncertainty**
- A migration-created `evidence_created` event uses migration commit time for `recordedAt`. Legacy capture timestamps remain source fields and are not promoted to verified DealFlow recording times without documented proof.
- A missing legacy status is not evidence of active status.
- Every migrated record receives a migration classification: `explicit_active`, `explicit_revoked`, `explicit_withdrawn`, `explicit_superseded`, `missing_status`, `unknown_status`, or `conflicting_legacy_data`. Classification is provenance, not a new lifecycle event type.
- Only explicit, internally consistent legacy statuses may be automatically projected. Missing, unknown, malformed, or conflicting status is quarantined and excluded from decisions until reviewed.
- For legacy revoked/withdrawn records with missing actor or reason, use a migration actor identity and a reason code such as `LEGACY_STATUS_IMPORT`, while explicitly marking actor/reason provenance as unknown. Never invent a historical person, time, or rationale.

**Supersession graph**
- Validate the complete graph before writing any migrated lifecycle events.
- Reject/quarantine dangling references, duplicate IDs, multiple successors, cycles, claim-identity mismatches, self-links, and inconsistent status/link combinations.
- A graph with unresolved errors is not partially committed. Independent, clean migration batches may proceed only if the migration report clearly isolates them and the batch boundaries are deterministic.

**Operational controls**
- Migration is a two-phase workflow: (1) dry-run report; (2) separately authorized commit against the exact source checksum and migration plan hash.
- The report includes totals for accepted, quarantined, rejected, and linked records; all unresolved IDs and reason codes; source checksum; schema/migration versions; and a deterministic mapping from legacy IDs to new IDs.
- Commit is idempotent for the same migration ID, source checksum, and plan hash. Reusing the migration ID with different inputs is an integrity error.
- Preserve a protected pre-migration backup and a tested recovery procedure. Recovery restores from the source backup into a new recovery generation; it does not delete already committed audit events or pretend the failed attempt never happened.
- No quarantined record is eligible for a recommendation. Manual resolution must itself be auditable and must not invent historical facts.

### 13.5 Server-authoritative protection is required for real-agent evidence

The approved target is a server-authoritative ledger, not a localStorage ledger later described as secure.

Required baseline controls:
- Authenticated actor identities and explicit authorization for each lifecycle operation.
- Server-assigned timestamps and monotonic ledger sequence.
- Database-enforced append-only permissions for application roles; no ordinary application role may update or delete committed evidence/event rows.
- Transactional atomicity for append and supersession.
- Optimistic concurrency or equivalent serializable transaction protection.
- Unique idempotency keys bound to canonical request hashes.
- SHA-256 event hash chain with documented canonical serialization and verification on reads, writes, exports, and restores.
- Periodic signed checkpoints whose signing key and storage permissions are separated from the primary database's administrative boundary.
- Protected backups with retention controls and tested restoration.
- Tenant isolation, least-privilege access, access logging, and operational alerting for integrity failures.
- No success response until durable commit and post-commit verification succeed.

A hash chain detects unauthorized or accidental alteration when a trusted checkpoint is available; it does not by itself prevent a privileged administrator from rewriting the full chain. Do not claim absolute immutability or non-repudiation. Describe the actual controls and their limits.

### 13.6 Privacy and retention boundary

- Do not place buyer names, phone numbers, email addresses, financial details, or other unnecessary personal data in immutable event metadata, hash-chain metadata, or checkpoint payloads.
- Store sensitive evidence payloads separately, encrypted at rest and in transit, with narrowly scoped access and auditable access logs. Lifecycle events should reference opaque evidence IDs and minimal reason codes.
- Define a retention schedule, lawful-erasure workflow, and jurisdiction-specific privacy review before admitting real-agent personal data. Where deletion or cryptographic erasure is legally required, preserve only the minimum legally permissible audit metadata and record the erasure operation without retaining the erased content.
- Tenant boundaries must be enforced server-side, not by client filtering.

### 13.7 Server/ledger outage behavior

Fail closed:
- A lifecycle operation is not successful until the server confirms durable commit and verification.
- Do not fall back to client-supplied status, localStorage, cached unverified events, or an offline queue represented as committed.
- If a recommendation cannot obtain a valid lifecycle projection and verified watermark, it must abstain or clearly report that a decision cannot be produced.
- A client may retain an explicitly labelled *pending, uncommitted request* for retry, but it must not display it as an event or use it to change eligibility.
- Retry only with the same idempotency key and canonical request. Surface conflicts for reload/review; never silently overwrite.
- Recovery and replay must verify the latest trusted checkpoint and the full event chain before serving decisions.
